# Paari Stage Outputs (Protocol v1.0)

Every stage consumes the previous stage's output, verifies it, and emits a schema-pinned artifact. Bundle collector: `app/proof_bundle.py::collect_proof_bundle(db, transaction_id)` and inspectable via `GET /v1/proof/{transaction_id}` (sender-constrained for protocol-v1 sessions: `Authorization: Bearer <session>` + `X-Paari-Proof`, enforced by `tests/test_sdk.py::test_sdk_v1_session_must_send_proof_for_proof_bundle`; owner-scoping by `tests/test_proof_bundle.py::test_proof_endpoint_exposes_bundle`).

> **Per-request, not per-arbitrary-string:** `transaction_id` is application-supplied and only unique per `(agent_id, idempotency_key)` (`app/models.py:267-269`). If a `transaction_id` is reused (e.g. velocity-REVIEW resubmission creates a second intent row), `collect_proof_bundle` and `GET /v1/proof/{transaction_id}` fail closed with `409 ambiguous transaction_id` — disambiguate via `GET /v1/audit/{transaction_id}`. The proof chain is per-payment-request.

> **Which bundle nodes are machine-validated:** `tests/test_proof_bundle.py::test_bundle_sections_satisfy_schema_required_keys` runs `tests/_schema_validator.py` over eight nodes — `discovery`, `parent_trust`, `delegation`, `agent_card`, `governance_decision`, `payment_result`, `audit_record`, `bounded_authorization`. The remaining six (`agent_identity`, `credential`, `authentication`, `payment_intent`, `payment_execution`, `revocation`) are DB/evidence projections with no schema pin. Where a row above still names a wire schema for one of them, that schema describes the object on the HTTP surface, not the bundle node.
